# Granite MVP 독립 앱 리뷰

검토일: 2026-10-23. 현재 판정: **발견 사항 해결 확인**(2차 수정 재검증). 아래 최초 발견과 1차 재검증은 당시 스냅샷의 기록이며, 최종 판정은 문서 끝의 2차 재검증을 따른다.

## 검토 범위와 근거

명세 `docs/superpowers/specs/2026-10-23-granite-mvp-design.md`, 작업 지시서, 신규 파일 리뷰 패키지, 실제 `src/` 전체, 단위 테스트, 제공된 구현 보고서를 대조했다. 브라우저 QA 담당자의 전체 E2E 실행을 중복하지 않았다. 저장 모델과 편집기의 두 결함은 별도 최소 재현으로 확인했다. 아래 줄 번호는 검토 시점 소스 기준이다.

### 1. [P1] 다른 탭의 성공한 저장이 충돌 초안을 삭제한다

- 위치: `src/storage/storage.ts:86-103`, `src/storage/workspace.ts:74-89`.
- 재현: 같은 저장소와 노트의 동일 기준본을 두 Workspace(A/B)에 로드한다. A에서 `tab A unsaved text`를 편집한다. B에서 `tab B saved text`를 편집하고 저장한다. A 저장은 정상적으로 충돌하지만, B가 공용 초안 키를 삭제했으므로 A를 새로고침하면 A의 내용은 복구되지 않는다.
- 최소 실행 결과: `A flush false status conflict persisted draft null`; 새 Workspace가 읽은 본문은 `tab B saved text`였다.
- 원인: 초안 키가 `[repositoryId, filename]` 하나뿐이다. 성공한 탭은 해당 키를 무조건 삭제하고, 충돌한 탭은 자신의 초안을 다시 보관하지 않는다. Web Locks는 디스크/데모 변경만 직렬화하며 초안 소유권을 보호하지 않는다.
- 영향: 충돌 화면은 초안 보관을 안내하지만 실제 브라우저 복구본은 사라진다. S10의 실패 초안 복구 약속을 위반한다.
- 권장 수정: 세션별 초안 또는 소유자/버전을 보존하는 복구 모델로 다른 작성자의 초안을 지우지 않도록 한다. 단순히 충돌 시 같은 공용 키에 다시 쓰는 것만으로는 양쪽의 실패 초안을 동시에 보호하지 못한다.
- 집중 테스트: 동일 저장소/노트의 두 Workspace 또는 브라우저 탭에서 서로 다른 초안 작성 → 한쪽 저장 → 다른 쪽 충돌 → 새로고침 후 충돌 초안 복구. 한 탭의 완료/버리기가 다른 탭의 초안을 삭제하지 않는 경우도 확인한다.

### 2. [P2] 제목 가져오기를 취소해도 늦은 응답이 URL을 변경한다

- 위치: `src/editor/Editor.tsx:412-451`, 취소 처리 `351-354`, `468-472`, `523-524`.
- 재현: URL 붙여넣기 → 제목 가져오기 → 응답 대기 중 Escape 또는 닫기 → 문서를 바꾸지 않고 응답 도착을 기다린다.
- 원인: 취소는 `pasteRef`를 비우지만 성공 응답의 `replace(p, title)`는 문서 리비전과 URL 범위, 잠금 상태만 검사한다. 요청/메뉴가 여전히 유효한지는 검사하지 않아 취소 직후에도 조건이 통과한다.
- 영향: 사용자가 보존하기로 한 URL이 자동 변환된다. S08의 Escape 동작 및 구현 보고서의 취소 보장과 다르다. 이 항목은 코드 경로로 확인했으며 별도의 브라우저 실행을 주장하지 않는다.
- 권장 수정: 활성 붙여넣기 요청 식별자 확인 또는 AbortController와 결과 무효화를 함께 적용한다.
- 집중 테스트: 지연된 응답을 제어하고 Escape와 닫기 각각 실행한 뒤 응답을 반환해 본문이 원래 URL 그대로인지 확인한다. 정상 성공과 편집 후 응답 무시도 유지한다.

### 3. [P2] 줄바꿈이 있는 정상 Markdown 링크를 프리뷰하면 앱 렌더링이 실패한다

- 위치: `src/editor/Editor.tsx:154-167`.
- 재현 문서: `before\n\n[first\nsecond](https://example.com)\n\nend`. 라이브 프리뷰로 열면 첫 줄이 활성 줄이고 링크는 비활성 구간이 된다.
- 확인: 실제 Editor를 jsdom/React로 마운트한 최소 재현에서 `Decorations that replace line breaks may not be specified via plugins`가 React의 uncaught-error 콜백에 전달됐다. 설치된 CodeMirror 구현 역시 `node_modules/@codemirror/view/dist/index.js:2804`에서 해당 제한을 검사한다.
- 원인: 정규식이 줄바꿈을 포함한 링크 라벨을 허용하며, ViewPlugin이 링크 전체를 하나의 replacement decoration으로 바꾼다. 이 종류의 플러그인은 줄바꿈을 가로지르는 replacement를 만들 수 없다.
- 영향: 보통 Markdown 파일에 존재할 수 있는 멀티라인 링크 하나로 편집기를 사용할 수 없으며, 초기 마운트 실패는 루트 화면까지 영향을 준다. 완전한 Markdown 확장 지원 제외 범위와 달리, 지원하지 않는 문법을 안전한 원문으로 남기지 못하는 가용성 문제다.
- 권장 수정: 멀티라인 링크에는 원문/안전한 마크 표시로 폴백하거나 줄바꿈 replacement를 허용하는 상태 필드 구조를 사용한다.
- 집중 테스트: 위 문서의 프리뷰 초기 마운트와 원문→프리뷰 전환에서 예외가 없는지 확인하고, 링크의 어느 줄을 편집해도 문서 내용이 보존되는지 검사한다.

### 4. [P2] 중요한 저장 상태와 목록 보조 텍스트의 대비가 너무 낮다

- 위치: `src/styles.css:575-587`, `src/styles.css:457-460`.
- 근거: 저장 상태는 9px 텍스트이며 `#a0aa94`/`#fbfaf7` 조합의 대비가 **2.32:1**, 미저장은 **2.77:1**, 실패/충돌은 **3.65:1**이다. 목록 본문 요약은 9px이고 `#a2aa96`/`#f1f2eb` 대비는 **2.14:1**이다. CSS 색상으로 상대 휘도 공식을 계산했다.
- 영향: 데이터가 저장됐는지 판단해야 하는 핵심 정보가 작은 글자와 낮은 대비로 제공된다. S12의 명확한 저장 상태·읽기 편한 서체 요구에 맞지 않는다.
- 권장 수정: 저장 상태와 실제 작업용 보조 텍스트를 일반 텍스트 대비 4.5:1 이상으로 조정하고, 데스크톱/좁은 창 모두 읽기 쉬운 크기로 높인다. 장식용 브랜드 문구까지 일괄 변경할 필요는 없다.
- 집중 검증: 저장 완료/미저장/저장 실패/충돌 상태의 계산된 색상 대비와 좁은 창에서의 크기·줄바꿈을 확인한다.

## 확인한 보호 장치와 범위

- 기존 리뷰의 데모 동시 생성/쓰기 문제는 저장소별 직렬화 큐와 Web Locks가 적용된 것을 확인했다. 초안 키 구분자 충돌도 JSON 튜플 키로 수정됐다. 위 1번은 그 수정과 별개인 같은 저장소·같은 노트의 복수 작성자 문제다.
- 대상 저장 후 원본 저장의 추출 순서, 대상 실패 시 원문 보존, 원본 실패 시 사본 알림, 추출 중 편집 잠금이 코드에 있다. 명세가 두 파일 원자 저장을 약속하지 않는 점도 유지된다.
- 파일명/제목 충돌 검사, 보통 사용자 파일에 메타데이터를 임의로 추가하지 않는 직렬화, 코드 구간의 위키링크 제외, HTTP(S)만 열기, HTML을 DOM으로 실행하지 않는 사용자 본문 표시를 확인했다.
- CORS 실패, 네이티브 권한 UI 자동화 한계, 제목 변경/삭제의 제외, 외부 프로그램과 파일 쓰기 사이의 완전한 원자성 부재는 이미 명시된 범위다. 이 항목들을 별도 결함으로 부풀리지 않았다.
- QA가 별도로 발견한 선택 텍스트 붙여넣기 메뉴 우선순위 문제는 본 리뷰의 독립 재현 항목으로 중복 계산하지 않았다.
- 전체 테스트/빌드 통과는 구현자 보고서에 기재된 증거이며 이 검토자가 다시 실행한 결과는 아니다. 네이티브 폴더 선택·권한 UI 검증도 주장하지 않는다.

## 재검증

### 1차 수정 재검증 — 2026-10-23

검토 범위는 `review-fixes.diff`, 변경된 저장/복구·편집기·CSS 코드 및 추가된 집중 단위 테스트로 한정했다. 전체 테스트/빌드/E2E는 컨트롤러와 QA가 실행하므로 중복 실행하지 않았다. 아래 두 저장 재현과 색상 대비 계산만 독립 실행했다.

| 최초 발견 | 판정 | 근거 |
| --- | --- | --- |
| 1. 타 탭 저장으로 충돌 초안 삭제 | **NOT ADDRESSED — 원래 재현은 해결됐지만 새 복구 경로에서 손실 발생** | 세션별 키로 서로 다른 탭의 본문은 보존된다. 그러나 새 초안 선택 동작이 현재 세션의 고유 편집 내용을 삭제한다. 아래 R1. |
| 2. 취소한 제목 요청이 URL 변경 | **ADDRESSED** | `replace`가 활성 `pasteRef`의 리비전도 확인한다. Escape/닫기로 ref가 비워진 뒤에는 적용하지 않는다. 두 취소 경로를 실제 Editor 대상으로 검증하는 테스트가 추가됐다. |
| 3. 멀티라인 링크 프리뷰 실패 | **ADDRESSED** | 줄바꿈 포함 링크는 replacement를 만들지 않고 원문을 유지한다. 비활성 줄 전환 테스트가 추가됐다. |
| 4. 저장 상태·보조 텍스트 대비 | **부분 수정 / NOT ADDRESSED** | 저장 상태는 11px, 대비 5.59:1, 미저장 5.70:1, 실패/충돌 5.44:1로 해결됐다. 목록 요약은 11px로 커졌으나 새 색상 `#717b65`의 대비가 기본 배경에서 3.95:1, 선택 배경에서 3.49:1로 아직 4.5:1 미만이다. |

QA의 선택 텍스트 URL 붙여넣기 문제도 custom paste handler의 `Prec.highest` 적용과 실제 선택 범위 별칭 테스트를 확인했으며, 변경 경로상 해결됐다.

#### R1. [P1] 다른 복구 후보 선택이 현재의 고유 미저장 편집을 지운다

- 위치: `src/storage/workspace.ts:115-129`, 특히 `129`의 기존 세션 키 덮어쓰기. UI는 `src/App.tsx`의 새 `복구할 초안` 선택 상자.
- 실제 재현: 같은 파일의 보관 후보 A/B 준비 → 새 Workspace에서 복구 → 현재 문서를 `A plus unique unsaved edits`로 편집 → B 선택(`restoreDraft(filename, b.owner)`).
- 독립 실행 결과: 선택 전 후보 본문 `[A, B, A plus unique unsaved edits]`; 선택 후 `[A, B, B]`. 고유 편집 내용은 메모리에서도, 브라우저 저장소에서도 사라진다. `edit`는 `recovered`를 지우지 않으므로 실제 UI에서도 해당 선택 상자는 계속 표시된다.
- 원인: `restoreDraft`가 현재 entry를 교체한 뒤 선택 후보를 현재 세션 소유 키에 기록한다. 현재 키의 이전 내용을 보존하거나 버리기 확인을 하지 않는다.
- 필요한 수정/테스트: 후보 선택 전에 현재의 독립 편집본을 별도 복구 가능한 후보로 보존한다. A/B 복구 → A 추가 편집 → B 선택 → 다시 추가 편집본 선택 또는 새로고침 후 해당 내용 복구를 검증한다. 단순히 기존 A가 남아 있는지는 충분하지 않다.

#### R2. [P2] 복구한 초안을 더 편집해 저장한 뒤 이전 초안이 다시 복구된다

- 위치: `src/storage/workspace.ts:21-37`, `74-79`; `src/storage/storage.ts:124-138`.
- 실제 재현: 이전 세션의 `recovered old` 초안 준비 → 새 세션에서 로드 → `recovered plus new work`로 편집하고 성공적으로 저장 → 다시 새 Workspace로 로드.
- 독립 실행 결과: 저장 후 다시 표시되는 본문은 `recovered old`, 상태는 `conflict`였다. 디스크의 최신 본문은 남아 있지만 사용자에게 이미 해결한 오래된 충돌이 반복된다.
- 원인: 복구한 후보의 출처/버전을 기록하지 않는다. 저장 후 새 본문과 정확히 일치하는 후보만 제거하므로, 이어서 편집한 이전 세션 후보는 영구히 남아 다음 시작 때 자동 선택된다.
- 필요한 수정/테스트: 실제 채택한 복구 후보와 그 스냅샷을 추적하고, 후속 저장 성공 또는 명시적 버리기 시 그 동일 스냅샷만 종료한다. 원래 소유자가 이후 수정한 다른 버전과 다른 후보는 보존해야 한다. 복구 → 추가 편집 → 저장 → 재시작에서 최신 저장본이 정상 표시되고 불필요한 복구 알림이 없는지 검증한다.

재검증 판정: **추가 수정 필요**. R1은 실제 편집 손실이므로 완료 전에 해결해야 한다. R2와 목록 요약 대비도 해당 수정 범위 안에서 보완할 수 있다.

### 2차 수정 재검증 — 2026-10-23

범위: R1/R2의 초안 수명 관리와 목록 요약 대비만 검토했다. 전체 앱 재감사나 전체 테스트 재실행은 하지 않았다.

- **R1 ADDRESSED:** 후보 전환 전에 현재의 다른 미저장 본문을 별도 불변 스냅샷으로 보관한다. 최소 재현을 다시 실행해 고유 편집본이 전환 뒤 남아 있고 그 후보를 다시 선택해 실제 본문으로 복구할 수 있음을 확인했다.
- **R2 ADDRESSED:** 복구 시 채택한 스냅샷의 키/버전과 이전 복구 출처를 추적한다. 저장 성공 후 해당 출처만 종료한다. 최소 재현에서 복구 → 추가 편집 → 저장 → 재로드가 최신 본문·`saved` 상태로 끝났으며 남은 초안은 없었다.
- **다른 작성자의 새 버전 보존 확인:** 원 작성자가 채택 이후 새 버전을 작성한 뒤, 복구 세션이 편집본을 저장하는 별도 최소 재현에서 원 작성자의 새 내용은 복구 후보에 남았다. 스냅샷 키에 버전이 포함되어 이전 참조를 종료해도 새 버전 키에 영향을 주지 않는다.
- **목록 요약 대비 ADDRESSED:** `#58664d`와 실제 배경을 다시 계산해 기본 5.45:1, 선택 4.82:1, hover 5.10:1, 선택 hover 4.66:1을 확인했다. 11px 크기 개선도 유지된다.
- 추가된 집중 단위 테스트는 고유 편집본 보관, 복구 출처 종료, 원 작성자의 새 버전 보존, 보관 후보의 복구 계보 종료를 다룬다. 전체 38개 통과는 구현자 보고이며, 여기서는 위 최소 재현을 독립 실행한 결과만 주장한다.

최종 범위 판정: **최초 네 발견 사항과 1차 수정 중 발견한 R1/R2가 모두 해결됐다. 이번 수정 범위에서 추가 차단 결함은 확인하지 못했다.** 네이티브 권한 UI를 포함한 이미 명시된 검증 한계는 그대로 적용된다.
